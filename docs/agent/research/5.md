# Research — Issue #5: Plaid sandbox verification harness

**PRD:** `docs/prd/plaid-integration.md` (FR1) · **North-star:** `docs/prd/PRODUCT.md` (Phase 1)
**Stage:** 2 (Research) · **Goal:** prove the real sandbox `link → exchange → sync` loop end-to-end, headless, without touching the default hermetic `pytest` run.

## 1. What already exists (grounding)

The plumbing is complete and unit-tested **against a mocked Plaid client only**:

- `app/services/plaid_service.py`
  - `get_plaid_client()` builds a `plaid_api.PlaidApi` from `settings.plaid_env` /
    `plaid_client_id` / `plaid_secret`. `PLAID_ENV_MAP` maps `"sandbox" → plaid.Environment.Sandbox`.
  - `create_link_token(client, user_id)` → `{link_token, expiration}` (products=`["transactions"]`, US, en).
  - `exchange_public_token(client, public_token)` → `{access_token, item_id}`.
  - `sync_transactions(client, db, plaid_item, user_id)` — cursor-based `transactions_sync`
    loop (`has_more`), upserts `Account` rows, adds/modifies/removes `Transaction` rows,
    dedupes via `_generate_dedupe_hash`, persists the cursor via `PlaidItemRepository.update_cursor`.
- `app/api/plaid.py` — routes: `POST /plaid/link-token`, `POST /plaid/exchange-token`,
  `GET /plaid/items`, `POST /plaid/items/{id}/sync` (also fires `EngineEvent.TRANSACTIONS_SYNCED`),
  `DELETE /plaid/items/{id}`.
- `app/config.py` — env prefix `FT_`; relevant keys `FT_PLAID_CLIENT_ID`, `FT_PLAID_SECRET`,
  `FT_PLAID_ENV` (default `sandbox`).
- `tests/test_plaid.py` (358 lines) — passes, but every Plaid call is `patch`-ed with a `MagicMock`.
- Dependency: `plaid-python>=29.0.0`.

**The gap:** nothing has ever hit real sandbox Plaid, so the loop is unproven against the actual
SDK response shapes (`.to_dict()` structures, `personal_finance_category`, pagination timing).

## 2. Headless sandbox flow (no Link UI required)

Plaid exposes a sandbox-only endpoint that mints a `public_token` directly, bypassing the Link UI:

1. **`/sandbox/public_token/create`** — `SandboxPublicTokenCreateRequest(institution_id, initial_products)`
   via `client.sandbox_public_token_create(req)` → returns a `public_token`.
   Use a standard sandbox institution, e.g. **`ins_109508`** ("First Platypus Bank"),
   `initial_products=[Products("transactions")]`.
2. **`item_public_token_exchange`** — reuse `exchange_public_token()` → `access_token` + `item_id`.
3. **`transactions_sync`** — reuse `sync_transactions()`; assert ≥1 `Account` and ≥1 `Transaction` land in the DB.

This is the same three calls the app already makes; the harness only substitutes the manual
Link handshake with `sandbox_public_token_create`. Imports needed:
`from plaid.model.sandbox_public_token_create_request import SandboxPublicTokenCreateRequest`
and the existing `Products`.

## 3. Design options

### Option A — pytest test, marker + env guard (RECOMMENDED)
`tests/test_plaid_sandbox.py::test_sandbox_link_exchange_sync`, decorated `@pytest.mark.plaid_sandbox`.
- **Deselect by default** so CI stays hermetic and network-free: add to `[tool.pytest.ini_options]`
  `addopts = "-m 'not plaid_sandbox'"` and register the marker under `markers = [...]`
  (avoids `PytestUnknownMarkWarning`).
- **Env guard:** `pytest.mark.skipif(not os.getenv("FT_PLAID_CLIENT_ID"), reason=...)` so even an
  explicit `-m plaid_sandbox` skips cleanly when creds are absent — no hard failure, no accidental
  network call.
- Owner runs it with one command: `FT_PLAID_CLIENT_ID=… FT_PLAID_SECRET=… pytest -m plaid_sandbox`.

### Option B — standalone script `scripts/verify_plaid_sandbox.py`
Run manually (`python -m scripts.verify_plaid_sandbox`). Simpler DB story, but a second run path to
maintain and no assertion harness. Acceptance criteria allow "a test **or** script"; A is preferred
because it reuses pytest's runner, skip semantics, and assertions, and lives beside the existing suite.

**Recommendation: Option A.**

## 4. Key risk — test DB / table creation

`tests/conftest.py` has an **autouse** `_setup_db` fixture that does
`Base.metadata.create_all(engine)` against `settings.test_database_url` (Postgres by default).
The 4 pre-existing `test_plaid.py` failures noted in PR #4 are SQLite-dialect `StatementError`s —
the models use Postgres-specific column types, so the harness **must run against a real Postgres**
(`FT_TEST_DATABASE_URL=postgresql://…`), not SQLite. The sandbox test can reuse the existing
`db_session` fixture (it already builds a sync `Session`, which is exactly what `sync_transactions`
expects). This is a documented owner precondition, not new work.

## 5. Other risks & mitigations

- **Sandbox transaction timing.** For a freshly created sandbox item, `transactions_sync` occasionally
  returns `has_more=false` with 0 transactions on the very first call before data settles. Mitigation:
  wrap the sync in a small bounded retry (e.g. up to ~5 attempts, short `time.sleep`) and assert on the
  accumulated count. Keep the retry inside the test, not in production `sync_transactions`.
- **Secrets.** Creds come only from env at run time; the harness commits **placeholder/sandbox** values
  only (nothing real). No `access_token` printed in assertion messages.
- **Isolation from CI.** The `-m 'not plaid_sandbox'` default plus the env-guard skip guarantees the
  default `pytest` invocation stays green and offline.
- **`expiration` typing.** `create_link_token` returns Plaid's `expiration` (a datetime); the harness
  need not assert on it, only that a `link_token` is returned (link-token creation is optional here —
  the headless flow uses `sandbox_public_token_create`, so link-token is a bonus assertion).
