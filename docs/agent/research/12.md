# Research — #12: Method Financial vs Plaid Liabilities for existing-card awareness

**Stage 2 (Research).** Issue: [#12](https://github.com/yinani24/finance-tracker/issues/12) ·
PRD: [`docs/prd/PRODUCT.md`](../../prd/PRODUCT.md) (Phases 3–4) · Date: 2026-07-07

## Why this matters

PRODUCT.md commits to recommending across **existing + new cards** and optimizing
**total first-year value**. To do that the recommender must know *which cards the user
already holds* and their terms (issuer, network, APR, limit, statement balance). Today
that data does not exist in our system:

- `app/models/card.py` (`Card`) is a **manually-entered** record — `name`, `network`,
  `issuer`, `annual_fee`, `rewards_config_json`. It has **no** balance / APR / limit /
  card-mask / `external_id`, and nothing populates it from a bank connection.
- There is **no** liabilities code anywhere (`grep liabilit app/` → nothing).

So existing-card awareness is greenfield. The question: source it from **Plaid
Liabilities** (reuse the Plaid item we already have) or add **Method Financial** (a
liabilities-specialist), or both.

## Option A — Plaid Liabilities

We already have Plaid wired end-to-end (Link, item, accounts, transaction sync). Adding
Liabilities is enabling the `liabilities` product on the Link token and calling
`/liabilities/get`.

**Credit-card fields returned** (`/liabilities/get` → `liabilities.credit[]`):
- APRs as an array of `{apr_type, apr_percentage, balance_subject_to_apr, interest_charge_amount}`
  where `apr_type ∈ {purchase_apr, cash_apr, balance_transfer_apr, special}`.
- `last_statement_balance`, `last_statement_issue_date`, `minimum_payment_amount`,
  `next_payment_due_date`, `is_overdue`, plus the account's `limit` / `balances`.

**Limits / caveats:**
- **APR is not provided by every issuer** — the array can come back empty.
- `last_payment_date` availability is limited.
- Liabilities carries **no transaction history** (that's the Transactions product we
  already use — fine, we get transactions separately).
- **Card-product identity is fuzzy.** Plaid gives an account *name* (often generic —
  "Credit Card", "Platinum Card") + institution, not a canonical product like "Chase
  Sapphire Preferred". Mapping to a row in `credit-card-bonuses-api` needs a matching
  heuristic (issuer + network + name tokens) with a manual-confirm fallback.

**Cost / onboarding:** zero new vendor, zero new keys, **no new user flow** — the owner
already links via Plaid. Liabilities is a per-product add on the existing item.

## Option B — Method Financial

Purpose-built for consumer **liabilities** — the exact domain of existing-card awareness.

- **Discovery model is fundamentally different:** user provides **legal name + phone**,
  passes MFA, and Method runs a **soft credit pull** (no score impact) to
  **auto-discover *all* liabilities** — credit cards, auto, student, mortgage, personal.
  **No bank-login credential sharing, no per-institution linking.** One verification →
  the full liability picture.
- **Coverage:** 15,000–20,000+ FIs, cited ~**95% of outstanding US consumer debt**.
- **Data:** standardized balances, due dates, **interest rates/APR ranges**, credit
  **limit**, minimum/payment amounts, **payoff quotes**, and (for supported accounts)
  transactions — normalized into one consistent model across institutions.
- **Real-time:** *Method Sync* pushes near-real-time balance/status updates via
  subscriptions.
- **Write capability:** can **initiate paydowns / payments** to connected liabilities —
  irrelevant to the recommender now, but strategically interesting later.
- **Pricing/onboarding:** **sales-led, no public pricing**, needs its own API keys and a
  separate identity-verification onboarding UX. Heavier to stand up than flipping a Plaid
  product flag.

## Recommendation

**Use Plaid Liabilities for the MVP.** Rationale:

1. **Zero marginal integration.** We already have the Plaid item, Link flow, sync, and
   webhook. Liabilities is a product flag + one endpoint — no second aggregator, no
   second onboarding, no sales cycle for a single-owner pre-launch app.
2. **It's sufficient for the recommender's need:** issuer, network, limit, APR (where
   available), and statement balance — enough to represent an existing card and compute
   its first-year value contribution.
3. **Method's superpowers don't pay off yet.** Soft-pull auto-discovery and paydown are
   compelling for a *debt-management* product; here they're nice-to-have. The place
   Method clearly wins — richer product identity — we can revisit if Plaid's fuzzy
   account names prove too weak for card matching.

**Design existing-card ingestion provider-agnostically** so Method (or a hybrid) can be
added in Phase 3+ without reworking the recommender. The recommender should read from our
own normalized model, never a vendor's raw shape.

## Plan to model "user's existing cards" (feeds Stage 3)

1. **New model `held_card`** (distinct from the manual `Card` catalog entry, or an
   extension of it) with: `user_id`, `account_id` (FK to the Plaid-synced credit
   account), `issuer`, `network`, `mask`/last4, `credit_limit`, `last_statement_balance`,
   `purchase_apr`, `balance_transfer_apr`, `cash_apr`, `min_payment`, `next_due_date`,
   `source` (`plaid` | `method` | `manual`), `external_id`, `matched_product_id`
   (nullable FK/slug into the card-bonuses dataset), `matched_confidence`, `synced_at`.
   Nullable fields → migration is additive and safe.
2. **`liabilities` provider interface** mirroring the enrichment pattern proposed in #11
   (`LiabilitiesProvider.fetch(user) -> list[HeldCardData]`), with a `PlaidLiabilities`
   impl and a `noop` default so tests stay hermetic/keyless.
3. **Product-matching step:** map each held card to a `credit-card-bonuses-api` product
   via (issuer + network + name-token) similarity, storing `matched_confidence`; low
   confidence → surface for manual confirmation rather than guessing.
4. **Feed the recommender:** engine compares first-year value of the user's *held* cards
   (using their real rewards config) against *candidate new* cards for the user's
   category spend — the "existing + new" comparison PRODUCT.md requires.

Suggested slices (separate issues): (a) enable Plaid Liabilities + `/liabilities/get`
fetch behind the provider interface; (b) `held_card` model + migration + upsert on sync;
(c) product-matcher against card-bonuses dataset with manual-confirm fallback.

## Risks

- **Card-product matching is the hard part**, provider-independent. Generic account names
  → some cards won't auto-match; need a manual-confirm path so we never silently attach
  the wrong rewards profile (which would corrupt recommendations).
- **APR gaps** (Plaid empty-array issuers) → recommender must tolerate missing APR
  (first-year *value* is mostly rewards + sign-up bonus, so APR is secondary unless the
  user carries a balance — worth confirming with owner).
- **Vendor lock-in** avoided only if the provider interface is honored — keep vendor
  shapes out of the recommender.
