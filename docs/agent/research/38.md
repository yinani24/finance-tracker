# Research — Issue #38: category-aware earn, resolving the card category-rate data gap

**Stage 2 (research).** Grounds the recurring "PRD Open Question 3" (category
reward rates) in the actual dataset and code, so the owner can pick a data path.

## Question
Rec-engine slice 3 wants to rank cards by how well their reward rates match the
user's category spend (dining first). Do we have the card-side per-category earn
rates to do this, and if not, where do they come from?

## Method
- Read `credit-card-bonuses-api/exports/data.json` (the card source of truth) and
  enumerated every top-level field across all cards.
- Read `finance-tracker` `app/services/card_recommendation.py`,
  `spending_profile.py`, and `enrichment/taxonomy.py` to confirm what the engine
  consumes vs. produces.

## Findings

### 1. The consumer side already exists (user category spend)
- `app/services/enrichment/taxonomy.py` defines a fixed 10-category internal set:
  `dining, groceries, travel, transport, shopping, bills, entertainment, health,
  income, other`. Provider labels (Plaid etc.) are mapped into it at the boundary.
- `app/services/spending_profile.py` aggregates a user's transactions into
  `category_breakdown` (share of spend per internal category) + `avg_monthly_spend`.
- So **we already know the user's dining/grocery/travel share of spend.** The
  "how much you dine out" signal is built and flowing (Phase-2 work: #23/#25).

### 2. The card side does NOT exist
- `app/services/card_recommendation.py:82` documents `category_breakdown` as a
  profile input but **never reads it**. Ongoing earn = flat `universalCashbackPercent`.
- `credit-card-bonuses-api/exports/data.json` — **179 cards**. Every top-level key:
  `annualFee, cardId, credits, currency, discontinued, historicalOffers, imageUrl,
  isAnnualFeeWaived, isBusiness, issuer, name, network, offers,
  universalCashbackPercent, url, details`.
- **No per-category earn structure of any kind** — no `categories`, `multipliers`,
  `rewardRates`, `bonusCategories`. The only ongoing-earn field is the flat
  `universalCashbackPercent`, distributed: **1% → 137 cards, 2% → 25, 1.5% → 15,
  5% → 2**.
- `details` is free-text, present on only **8 / 179** cards, and holds miscellany
  ("Previously SavorOne", "Only cashback redemption"). The stray "dining"/"5x"
  substring hits live here and are **not machine-readable rates**.

### 3. Upstream cannot be enriched (kills PRD Open Question 3 option (a))
`credit-card-bonuses-api/README.md`: *"This repository is a read-only mirror. Data
is generated and synced daily from a private monorepo. Pull requests will not be
accepted here."* License is **MIT + Commons Clause** (non-commercial only).

→ We **cannot** contribute per-category rates upstream. The PRD's preferred path
("enrich the sibling API") is not available. Category rates must come from
somewhere we control, or a different source.

## The gap, precisely
We know **how the user spends by category** but have **no card-side category
reward rate to match against**, and the source of truth structurally does not
provide one and will not accept one.

## Options
- **(A) — RECOMMENDED — In-repo curated category-rate table (top ~20–30 cards).**
  Add `app/data/card_category_rates.json` keyed by `cardId` → `{internal_category:
  multiplier}` for the highest-value / most-popular cards (e.g. a dining-4x card →
  `{"dining": 4}`). Long tail falls back to flat `universalCashbackPercent`.
  - *Pros:* delivers the dining-first promise for the cards that matter; zero
    dependency on an un-contributable upstream; unit-testable now; small.
  - *Cons:* manual curation + periodic refresh. Bounded — a curator already has to
    eyeball sign-up bonuses; category rates change rarely.
- **(B) Alternative dataset** with structured category multipliers. Investigated
  this run (see "Follow-up: option (B) investigation" below) — **no clean,
  license-compatible, US-focused, maintained per-category earn-rate dataset
  surfaced.** In practice (B) reduces to "integrate a paid/commercial API
  (licensing review)" or "adopt a scraper (maintenance + ToS risk)," both heavier
  than (A) with no clear data-quality upside.
- **(C) Defer** category-awareness; ship flat-cashback recs (slice 2 / #37) as v1.
  Honest fallback, but the core "recommend based on how you dine out" promise does
  not ship until a data source exists.

## Recommendation
**(A).** Smallest slice that makes the product's core premise real. Reuse the
`_ongoing_value` helper from #35 as the single source of truth: category-aware calc
for curated cards, flat fallback otherwise, so `recommend_next_card` and
`analyze_portfolio` stay consistent. (C) is the honest default if the owner would
rather not maintain curated data; (B) only if a good source is known.

## Risks / notes
- Curated data provenance: document where each rate came from + a refresh cadence;
  category rates are static enough that quarterly review is plenty.
- Keep it additive: flat-only cards must score exactly as today (regression-safe).
- Commons Clause applies to the *upstream card data*, not to a rate table we author.

## Follow-up: option (B) investigation — is there a dataset we can just adopt?

The findings above grounded **(A)** and **(C)** but left **(B)** as an unexamined
"if a good source is known." To keep the A/B/C pick from being decided on a blank,
this run went looking for an existing structured category-earn-rate dataset that is
**US-focused, license-compatible (this repo is MIT + Commons Clause / non-commercial),
and maintained.** None of the candidates cleared all three bars:

| Source | US? | Per-category earn rates? | License | Verdict for (B) |
|---|---|---|---|---|
| [ccreward-web / ccreward.app](https://github.com/aashishvanand/ccreward-web) | ❌ India + Singapore only | Yes (MCC-based) | Dual — non-commercial free / **commercial paid** | Wrong geography; commercial gate |
| [MyCardBook](https://github.com/pthakkar9/mycardbook) | ✅ | ❌ — tracks **statement credits/benefits** (Uber, Resy…), not earn multipliers | MIT | Wrong shape (~22 cards, benefit tracking) |
| [DealyDigests](https://github.com/pravinl23/DealyDigests) | ✅ | Unconfirmed — app code; no documented structured rate file (`public/data` path 404s) | MIT | Hackathon-style app, not a maintained dataset |
| [API-CreditCardRewardsScraper](https://github.com/kaburkett/API-CreditCardRewardsScraper) | ✅ | Yes, but **scraped live from issuer sites** | — | Unmaintained; freshness/coverage/ToS risk |
| [rewardscc.com / Rewards CC API](https://rewardscc.com/) | ✅ ~99.5% coverage | Yes | **Commercial / paid API** | Best coverage but paid + licensing to vet |
| [greggles/mcc-codes](https://github.com/greggles/mcc-codes) | ✅ | ❌ — MCC code list only (no rates) | Public | Useful *mapping aid*, not an earn-rate source |

**What this means for the decision.** Option (B)'s premise — "there's an existing
structured dataset we can just adopt" — has **no clean, license-compatible target.**
The only broad, structured US source (rewardscc) is a paid API whose terms would
need vetting against this repo's non-commercial Commons Clause and any future
commercial intent. So (B) is really "integrate a commercial API (licensing review)"
or "take on a scraper (maintenance + ToS risk)" — both strictly heavier than **(A)**
(a small in-repo curated table for the top ~20–30 cards) with no clear data-quality
upside. This **strengthens the standing recommendation of (A)** and makes **(C)**
(ship flat-cashback v1) the honest lighter fallback. It does **not** decide anything —
still the owner's **(A)/(B)/(C)** call.
