# Research — #209 Trajectory: category trends + recurring-commitment detection + cash-flow projection

**Stage 2 (research).** Plan Phase 3. Gated on owner **Q1** (trajectory scope) in
`docs/prd/data-architecture-and-evolution.md`. This note grounds the design in the current
code, proposes a **bounded, recommendation-serving** shape (not a general forecaster), and
breaks it into shippable slices so implementation can start the moment Q1 is confirmed.

## 1. Ground truth (what the code does today)

- **`app/services/spending_profile.py` is a single-window snapshot.** `compute_profile`
  aggregates non-income txns over a **6-month lookback** (`_lookback_start`, first-of-month N
  months ago) into one row: `avg_monthly_spend`, `category_breakdown_json` (monthly-avg $ per
  category), `category_counts_json`, `top_merchants_json`. No month-over-month, no history, no
  recurring detection, no projection. This is exactly limitation **L4**.
- **Storage is one row per user.** `app/models/spending_profile.py` has
  `UniqueConstraint("user_id", ...)` and the repo `upsert`s it. There is **no time series** —
  each recompute overwrites the prior snapshot. So trends need either a new history table or an
  on-the-fly monthly bucketing pass (see §3).
- **The recommender already keys off `category_breakdown`.** `card_recommendation.py`
  (`_estimate_category_earn`, lines ~245–290; `recommend_next_card` ~330; `analyze_portfolio`
  ~463) distributes `avg_monthly_spend` across `category_breakdown` and, when a card lists
  per-category rates, earns each category at its own rate — falling back to the flat number when
  no breakdown/rates exist. **This is the exact hook a trend signal plugs into:** a
  trend-weighted breakdown (or a per-category multiplier) changes earn estimates with *zero*
  change to the recommender's contract. `card_insight_engine.py:51` also reads the breakdown.
- **Data model supports all three features with no schema change to `transactions`.**
  `Transaction` already has `occurred_on` (Date), `amount` (Float), `category`,
  `normalized_merchant`, `is_income`, `is_savings`. Recurring detection reads
  `normalized_merchant` cadence; projection reads income cadence (`is_income=True`) + category
  run-rates; trends read `occurred_on` month-bucketed `category`.

## 2. Bounded scope proposal (directly answers Q1)

`PRODUCT.md` lists forecasting as out-of-scope. Recommend confirming a **narrow,
explainable, recommendation-serving** version and *nothing more* — so it does not drift into a
Range/Arta-style planner (the doc's own §3a "Range is the north-star for depth, but keep ours
recommendation-serving" framing):

- **IN:** (a) per-category **monthly trend series** + MoM / trailing-quarter delta;
  (b) **recurring-commitment detection** over `normalized_merchant` (cadence → subscription/rent),
  incl. duplicate-subscription flagging; (c) a **single, simple, explainable next-month
  cash-flow projection** = projected income − recurring commitments − per-category run-rates.
- **OUT (keep out):** multi-month/horizon forecasting, scenario planning, ML time-series
  (ARIMA/Prophet), goal projection, net-worth trajectory. Every number must be reconstructable
  by hand from the txn ledger (explainability is the guardrail that keeps scope bounded).
- **Success guardrail:** a trend only earns its keep if the **recommender cites it** (AC2:
  "dining trending +15%/qtr → dining multiplier matters more"). If a metric can't feed a
  recommendation rationale or a user-facing "trending up/down" badge, it's out of scope.

## 3. Design options (the one real architecture decision)

How to produce monthly history given the single-row snapshot model:

- **Option A — compute-on-read (recommended for the spike/MVP).** A new
  `compute_category_trends(db, user_id, months=6)` runs one grouped query
  (`GROUP BY date_trunc('month', occurred_on), category`) and returns a
  `{category: [{month, amount, count}]}` series + MoM deltas. **No migration, no new table**,
  always consistent with the ledger, cheap at personal-finance data volumes (hundreds–low
  thousands of rows). Downside: recomputed each request (fine; can memoize like
  `get_or_refresh`).
- **Option B — persist a `spending_profile_history` table** (one row per user×month×category).
  Needed only if we later want snapshotting-at-time or expensive derived metrics. **Defer** —
  it's a migration + backfill for no MVP benefit. Note the existing `UniqueConstraint(user_id)`
  on `spending_profiles` means the *current* table can't hold history; history is a *separate*
  table if/when we go this route.
- **Recommendation:** **Option A.** Ship trends/recurring/projection as pure read-time services
  (mirrors how `card_recommendation` is stateless over the profile). Revisit B only if a
  concrete need for stored history appears.

**Recurring detection (Option A-style):** group non-income txns by `normalized_merchant`; flag
recurring when ≥3 occurrences at a near-constant cadence (~monthly/weekly/annual) and stable
amount (±~15%). Duplicate-subscription flag = two distinct `normalized_merchant`s mapping to the
same known-service token (e.g. two streaming subs) — reuses the merchant-normalization work
already merged (#207/#212). Risk: `normalized_merchant` is nullable → fall back to `merchant`.

**Projection (explainable one-liner):** `next_month ≈ Σ recurring_commitments +
Σ per-category trailing-3mo run-rate − projected_income_cadence`. Every term is displayable, so
the UI can show *why*. No smoothing model beyond a trailing mean.

## 4. Slice breakdown (each a small, hermetic-testable PR once Q1 = yes)

1. **Backend — category trend series.** `compute_category_trends` + a `GET
   /profile/trends` (or extend the existing profile endpoint) returning per-category monthly
   series + MoM/quarter deltas. Pure function over seeded txns → fully hermetic tests (no
   Plaid/Postgres beyond the standard fixtures). **Do this first** — it's the input to 2 & 3.
2. **Backend — recurring-commitment detection.** Cadence detector over `normalized_merchant`
   + duplicate-subscription flag. Hermetic tests on synthetic cadences.
3. **Backend — cash-flow projection.** Combines 1 + 2 + income cadence into one projected
   figure with a breakdown. Hermetic.
4. **Recommender integration (the point).** Feed a trend signal into `category_breakdown`
   weighting (or a per-category multiplier) so `recommend_next_card` / `analyze_portfolio`
   cite trends in rationale — satisfying **AC2**. Additive; falls back to today's behavior when
   <3 months of data.
5. **Frontend.** Per-category trend charts, a projection tile, a trending-up/down badge the
   recommender rationale can reference (satisfies **AC1**). Frontend-only, provable from code.

Sequencing 1→2→3→4→5 keeps every PR independently reviewable and each strictly additive to a
green trunk.

## 5. Risks / watch-items

- **Data sufficiency (AC1 needs ≥3 months).** Every surface must degrade gracefully with <3
  months: hide trend/projection UI, and the recommender falls back to the flat breakdown. Bake
  an explicit `insufficient_history` state into the trend response from slice 1.
- **Time-window correctness.** The profile service just had a time-bomb-fixture incident
  (run 2026-08-02T02-18Z / PR #220): fixtures seeded absolute dates that aged out of a
  `date.today()` lookback. Trend code MUST take an injectable `today`/`as_of` (as
  `compute_profile` already does) and tests MUST anchor seed dates relative to it — do not
  repeat absolute-date fixtures.
- **Category dependence.** Trend quality is bounded by classification quality (L2 / #208). A
  category that's mostly `other` produces a useless trend. Trends amplify the value of #208 but
  don't block on it.
- **Currency/points denomination.** If any trend value is ever converted to reward value, reuse
  the card-currency denomination rule fixed in #201/#219 — don't re-derive it.

## 6. Recommendation

Confirm the **bounded Q1 scope** in §2, then implement **Option A (compute-on-read, no
migration)** in slices 1→5, starting with the trend series (slice 1). This delivers the
"where am I heading" capability and the trend-weighted recommender (AC2) with minimal new
surface and zero schema risk, and stays firmly inside "recommendation-serving, not a general
forecaster."
