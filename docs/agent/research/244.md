# Research — #244: render the multi-card combination recommender (client-only web)

**Stage:** 2 (Research) → 3 (Plan). **Depends on #243 merging** (adds
`POST /recommendations/combination/stateless`). Cut the implementation branch
from `origin/main` *after* #243 lands.

## Goal
Make the combination recommender (`optimal_card_combination`, #185 — PRODUCT.md
Decision #1, the "optimal *set* of cards") visible in the client-only flow. The
next-card recommender is the only thing the recommendations page renders today;
`postStatelessPortfolio` exists in the client but is unused, and combination has
**no** client method, types, or UI.

## Backend contract — verified against the real code (no drift from #244's spec)
The TS types proposed in the issue match the backend exactly. Verified against
`apps/api/app/schemas/recommendation.py` and the dict actually returned by
`CardRecommendationService.optimal_card_combination` /
`_route_wallet` on `main`:

- `RecommendedNewCard` = `{ name: str, issuer: str, marginal_value: float,
  categories_won: List[str], rationale: str }`
  (`recommendation.py:115`).
- `RoutedCategory` = `{ category: str, card: BestHeldCard, is_new: bool,
  rate: float }`, where `BestHeldCard = { name, issuer }`
  (`recommendation.py:103`, `:79`). Confirmed the runtime dict nests `card` as
  `{"name", "issuer"}` — `card_recommendation.py:719` (`_route_wallet`).
- `CombinationResponse` = the four keys above +
  `baseline_first_year_value: float`, `projected_first_year_value: float`,
  `spending_profile` (`recommendation.py:128`).
- The **stateless** endpoint returns the combination dict **verbatim and omits
  `spending_profile`** (mirrors next-card/portfolio stateless — caller already
  holds the profile it posted). So `StatelessCombinationResponse` intentionally
  drops `spending_profile`, exactly as #244 states.

### Units — the trap to avoid
- `marginal_value`, `baseline_first_year_value`, `projected_first_year_value`
  are **USD dollars** → render with `formatCurrency` (`src/lib/format.ts`).
  Do **not** append `"pts"` (this is the #197 fix — the engine already converts
  points to cash at `points_value_cents`).
- `rate` (in `per_category_routing`) is already a **percent-equivalent number**
  (e.g. `3.0` means 3%), per the `_route_wallet` docstring. Render as
  `` `${rate.toFixed(1)}%` `` — **do not multiply by 100.**

## Frontend wiring — verified patterns to mirror
- **Profile source (reuse verbatim):** the page already builds a
  `StatelessProfileRequest` inside its next-card `useQuery`
  (`page.tsx:50-64`): `avg_monthly_spend: summary.monthlySpend`,
  `category_breakdown` from `cats.map(c => [c.category, c.total/summary.months])`,
  `held_cards` from `session.heldCards` (using `productName ?? name` — "the
  dataset is keyed on the product name, not the display label"),
  `credit_score_band`, `recent_card_applications`. The combination call uses this
  **same object**. Factor it into a `buildProfile()` memo so both queries share
  one source of truth (avoids the two calls drifting).
- **Client method** — add to `src/lib/api.ts` next to `postStatelessPortfolio`
  (`api.ts:284`), reusing `StatelessProfileRequest` (`api.ts:237`):
  ```ts
  export interface StatelessCombinationResponse {
    recommended_new_cards: {
      name: string; issuer: string;
      marginal_value: number; categories_won: string[]; rationale: string;
    }[];
    per_category_routing: {
      category: string; card: { name: string; issuer: string };
      is_new: boolean; rate: number;
    }[];
    baseline_first_year_value: number;
    projected_first_year_value: number;
  }
  export const postStatelessCombination = (body: StatelessProfileRequest) =>
    request<StatelessCombinationResponse>(
      "/recommendations/combination/stateless",
      { method: "POST", body: JSON.stringify(body) },
    );
  ```
- **UI** — second `useQuery` on `page.tsx` (or a `<CombinationPanel>` child),
  `enabled: hasData && hasApi`, keyed on the same inputs as the next-card query
  so both invalidate together. Render:
  - Headline: `formatCurrency(baseline)` → `formatCurrency(projected)` with the
    uplift (`projected − baseline`).
  - Recommended new card(s): name, issuer, `formatCurrency(marginal_value)`,
    `categories_won`, `rationale`.
  - Per-category routing table: category → `card.name` (`card.issuer`),
    `` `${rate.toFixed(1)}%` ``, with `is_new` rows visually flagged.
  - **Empty/optimal state:** `recommended_new_cards.length === 0 &&
    projected_first_year_value === baseline_first_year_value` → "your current
    wallet is already optimal — no card to add." (Also the `avg_monthly_spend
    === 0` path, which the service early-returns to baseline.)

## Risks / notes
- **Modified Next.js.** `apps/web/AGENTS.md`: "This is NOT the Next.js you know
  — read the relevant guide in `node_modules/next/dist/docs/` before writing any
  code." Do that during implementation before touching routing/data-fetching
  idioms.
- **Order dependency.** The endpoint ships in #243; the client method compiles
  and lints fine without it (it's a runtime call), but don't merge the web slice
  before #243 or the UI 404s at runtime. Branch off `origin/main` after #243.
- **Contract stability.** #243 is `mergeable_state: clean`, CI green, no review
  comments — low risk of shape change before merge. If review reshapes the
  endpoint, re-check the four keys above before implementing.
- **No new persisted state** — consistent with the stateless flow (non-goal:
  DB-backed `GET /recommendations/combination` wiring).

## Recommendation
Contract is exact and the wiring points are all confirmed present — this is a
near-mechanical slice once #243 merges. Implement as: (1) `api.ts` method +
type, (2) shared `buildProfile()` memo, (3) combination `useQuery` + render
block/child, (4) `CHANGELOG.md`. Verify with `npm run lint` + `npm run build`
on touched files. No owner decision required.
