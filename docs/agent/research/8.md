## 2. The Plaid verification protocol (what we must implement)

Plaid signs every webhook with a JWT in the **`Plaid-Verification`** request header. Verification steps (order matters — cheap/structural checks first, network + crypto last):

1. **Read the JWT, check `alg`.** Decode the JWT *header* only (`jwt.get_unverified_header`). Assert `alg == "ES256"`. Reject anything else (defends against `alg=none` / `HS256`-confusion attacks — never let the library pick the alg from the token).
2. **Extract `kid`** from the JWT header — this is the Plaid **`key_id`** that signed the request.
3. **Fetch the verification key** via `/webhook_verification_key/get` with that `key_id` (env-scoped: sandbox keys ≠ production keys — uses the same client credentials as the rest of the service). Returns a JWK.
4. **Cache the key by `key_id`.** Do **not** fetch per request. Cache miss → fetch; hit → reuse (see §4 rotation).
5. **Verify the JWT signature** against the JWK using ES256, and extract the (now-trusted) payload. Invalid signature → reject.
6. **Replay window:** check the `iat` (issued-at) claim is **within 5 minutes** of now. Older → reject. (PyJWT does *not* enforce a max-age on `iat` automatically — we check it manually.)
7. **Body integrity:** extract `request_body_sha256` from the verified payload, compute `sha256(raw_body).hexdigest()`, and compare **constant-time** (`hmac.compare_digest`). Mismatch → reject. This is what binds the signed JWT to *this specific* payload.

Only if all pass → authentic → `verify_webhook` returns `True`.

### JWK shape returned by `/webhook_verification_key/get`
The `key` object is a P-256 EC public key in JWK form:
`kty: "EC"`, `crv: "P-256"`, `use: "sig"`, `alg: "ES256"`, `kid`, `x`, `y`, plus `created_at` and **`expired_at`** (null while active; set to a timestamp once Plaid schedules the key for rotation).

## 3. Gotchas that will silently break verification

- **Hash the raw bytes, never a re-serialized body.** `request_body_sha256` is sensitive to whitespace/formatting. Plaid documents that its bodies use **2-space** indentation; if we `json.loads` then `json.dumps` (which defaults to different spacing) and hash *that*, the digest will never match. The #7 route already hands `verify_webhook` the raw `await request.body()` bytes — **keep it that way**; hash `body` directly, and only parse to `PlaidWebhookPayload` *after* verification.
- **`alg` confusion.** Pass `algorithms=["ES256"]` explicitly to the JWT verify call; never trust the token's own `alg`.
- **`iat` is not auto-enforced.** PyJWT validates `exp`/`nbf` if present, but Plaid's JWT carries `iat` + `request_body_sha256`, not `exp`. We enforce the 5-minute replay window ourselves.
- **Constant-time hash compare** (`hmac.compare_digest`) to avoid a timing side-channel on the body hash.
- **Env-scoped keys.** `/webhook_verification_key/get` returns different keys per Plaid environment; using the sandbox client for a production `key_id` (or vice-versa) yields a key that won't validate.

## 4. Key caching & rotation (design)

Plaid rotates signing keys and may sign a webhook with a **new `kid`** at any time. Because the `kid` travels in each JWT header, a rotation naturally shows up as a **cache miss** → fetch-on-miss handles it with no extra machinery:

- **Recommended (MVP):** a process-local `dict[str, dict]` mapping `kid → JWK`. Miss → call `webhook_verification_key_get(key_id=kid)` and store. This is correct because a rotated key = new `kid` = miss = fetch. `expired_at` does **not** need proactive purging for correctness (an expired key is only ever requested if a JWT references its `kid`, and Plaid keeps expired keys resolvable long enough to validate recently-sent webhooks).
- Cache is per-worker (uvicorn processes don't share memory). Fine for the single-owner MVP — worst case is one extra fetch per worker per new `kid`. A shared cache (Redis) is out of scope; note as a scale-later item.
- Optional hardening (not required to pass AC): a small TTL so a key marked `expired_at` eventually re-validates against a fresh copy. Keep it simple unless the owner wants it.

## 5. The config flag — `FT_PLAID_WEBHOOK_VERIFY` (defaults **enabled**)

Add to `app/config.py`:
```python
plaid_webhook_verify: bool = True   # env: FT_PLAID_WEBHOOK_VERIFY (prefix FT_)
```
`verify_webhook` short-circuits to `True` when the flag is off — the escape hatch for exercising the endpoint locally/in sandbox without minting a real Plaid JWT (PRD Q3 assumption: defaults **on**).

### ⚠️ Interaction with #7's existing tests (must handle in the plan)
Today `verify_webhook` always returns `True`, so #7's webhook tests POST unsigned bodies and get 200. The moment #8 makes verification **default-on**, those same tests would hit the new `401` path and break. The plan must therefore:
- set `plaid_webhook_verify = False` for the **existing** #7 functional tests (a fixture/override or env), so they keep asserting sync behaviour without minting JWTs, **and**
- add **new** #8 tests (below) that exercise verification with the flag **on**.

This is the single most likely source of a red suite when #8 lands — calling it out now.

## 6. Where the Plaid client comes from inside `verify_webhook`

`verify_webhook(headers, body)` currently takes no client/db, and the route seam should stay that way (#7 promised "#8 slots in without touching the route"). To call `/webhook_verification_key/get`, `verify_webhook` should obtain a client the same way the service layer does — reuse the existing `get_plaid_client()` factory (already used in `app/api/plaid.py` / `plaid_service.py`) inside the function. Keeps the route signature untouched.

- Minor: `verify_webhook` is sync and called without `await` in the async route, so the SDK key fetch briefly blocks the event loop. Acceptable for the single-owner MVP; note as a future async/offload item, not a blocker.

## 7. Test strategy (hermetic — no network, no real Plaid)

Mint a throwaway EC P-256 keypair **in the test** with `cryptography`, sign a JWT with it, and mock `webhook_verification_key_get` to return the matching JWK. This exercises the real crypto path with zero secrets and zero network.

Helper sketch:
```python
from cryptography.hazmat.primitives.asymmetric import ec
import jwt, hashlib, json, time

priv = ec.generate_private_key(ec.SECP256R1())
pub_jwk = json.loads(jwt.algorithms.ECAlgorithm(jwt.algorithms.ECAlgorithm.SHA256).to_jwk(priv.public_key()))
pub_jwk.update({"kid": "test_kid", "use": "sig", "alg": "ES256"})

def sign(body: bytes, iat=None, kid="test_kid"):
    claims = {"iat": iat or int(time.time()),
              "request_body_sha256": hashlib.sha256(body).hexdigest()}
    return jwt.encode(claims, priv, algorithm="ES256", headers={"kid": kid})
```
(Mock `webhook_verification_key_get(key_id="test_kid")` → an object whose `.key` is `pub_jwk`.)

Cases:
- **Valid** JWT + matching body hash + fresh `iat` → `verify_webhook` True → endpoint 200 + sync fires.
- **Tampered body** (hash mismatch) → **401**.
- **Bad signature** (JWT signed by a *different* key than the JWK returned) → **401**.
- **Missing `Plaid-Verification` header** → **401**.
- **Stale `iat`** (> 5 min old) → **401**.
- **Wrong `alg`** (e.g. an HS256 token) → **401**.
- **Flag disabled** (`FT_PLAID_WEBHOOK_VERIFY=false`) → verification skipped, endpoint 200 with an unsigned body.
- **Key cached by `key_id`:** two webhooks with the same `kid` → `webhook_verification_key_get` called **once** (assert the mock's call count).
- All existing #7 + `test_plaid.py` tests still pass (with the flag set off for the #7 functional cases per §5).

Note (from #7 PR): the models use PG-specific column types, so the suite runs against a real Postgres (`FT_TEST_DATABASE_URL`), not SQLite — same as #10/#13.
