# Research — #11: Transaction-enrichment layer (Ntropy vs Spade)

_Stage 2 research for issue #11. Originally posted as an issue comment (2026-07-07);
persisted here now that it ships alongside the slice-1 implementation. Grounded in the
current codebase + provider docs/announcements (July 2026)._

Ref: `docs/prd/PRODUCT.md` (Phase 2 — spending intelligence, dining first).

## Where enrichment plugs into our code

The schema is already enrichment-ready. `app/models/transaction.py` carries the exact
target columns: `merchant` (raw), `normalized_merchant`, `category` (`String(50)`),
`external_id` (Plaid `transaction_id`), `source`, `dedupe_hash`.

Today categorization is just `personal_finance_category.primary` from Plaid, lowercased,
in `sync_transactions` (`app/services/plaid_service.py`). That is the weak signal the
owner flagged. An enrichment layer overwrites `category` + `normalized_merchant` (and,
in slice 2, adds `category_confidence` / `enriched_at`) **without schema upheaval** — no
new table required for the MVP.

`app/services/spending_profile.py` groups habit metrics by `t.category` — so the moment
`category` improves, the Phase-2 dining metric improves for free, with no consumer change.

## Provider comparison

| | **Ntropy** | **Spade** |
|---|---|---|
| Positioning | General consumer/SMB enrichment (Mercury, Ramp) | Card-auth-grade merchant intelligence (Cash App, Stripe, Bilt); $40M Series B (Mar 2026) |
| Historical/stored txns | Batch API — sync ≤4,000 / async ≤~25,000 per batch; Python SDK w/ auto-pagination, retries | Batch enrichment endpoint — ≤50,000 txns/request, completion callback, ≤10 req/s |
| Output fields | Cleaned merchant, category (+ confidence), entity/logo; toggleable fields; custom categories | Clean merchant, category/industry, location; proprietary merchant DB; custom industry system |
| Category taxonomy | Two-tier general + accounting; consumer categories vary by account-holder type; custom categories can replace defaults | Proprietary industry system, strong where MCC is weak |
| US coverage / accuracy | "Most accurate" (self-reported); strong US | 99.9% US+CA merchant coverage, 99%+ accuracy (self-reported) |
| Latency | Batch-oriented (fine for async backfill) | P99 <40ms real-time (overkill for us) |
| Free/trial | **2,000 txns free**, no-commitment tiers after | No public free tier; usage-based + platform fee, sales-led |
| Self-host | Hosted API (data leaves our infra) | Hosted API (data leaves our infra) |

## Recommendation

**Start with Ntropy for the MVP**, behind a provider-swappable interface.

- The **2,000-txn free tier** lets us prototype dining accuracy on real (sandbox/personal)
  data with zero procurement — no sales call. Spade is sales-led with no free tier, which
  stalls a single-owner MVP.
- Both are batch-capable over our **stored** transactions, so neither forces us into a
  card-auth stream (we don't have one — we ingest post-hoc via Plaid sync).
- Ntropy's confidence score + custom categories map cleanly onto our "dining first" habit
  metrics.
- Keep Spade as the documented fallback if Ntropy's dining accuracy disappoints — its
  merchant DB is best-in-class and the `enrichment` interface makes the swap a one-file
  change.

## Interface (implemented in slice 1 — this PR)

`app/services/enrichment/` — `base.py` (`EnrichmentInput` / `EnrichmentResult` +
`EnrichmentProvider` Protocol), `noop.py` (keyless default, echoes raw Plaid values),
`taxonomy.py` (fixed internal set + `map_to_internal`), `__init__.py` (`get_provider`
factory keyed off `FT_ENRICHMENT_PROVIDER`). The interface is **synchronous** — deviating
from the Stage-3 plan's `async def enrich` — because the sole caller, `sync_transactions`,
runs in a synchronous request path; forcing an event loop there would be error-prone. A
network-backed provider makes its HTTP calls synchronously instead.

## Slice 2 (deferred — gated on owner answers below)

1. `NtropyProvider` (or Spade) implementing the interface, with the taxonomy mapper applied
   at the boundary.
2. Migration: `category_confidence FLOAT NULL` + `enriched_at TIMESTAMP NULL` (nullable →
   safe, no backfill needed to deploy).
3. One-shot `enrich_existing` backfill command for rows where `enriched_at IS NULL`
   (batch, rate-limit aware).

## Risks

- **Data privacy:** both providers are hosted — raw merchant strings + amounts leave our
  infra. For a personal-finance app that is a real consideration; neither offers advertised
  self-host.
- **Taxonomy drift:** vendor categories ≠ our internal set → the mapper is load-bearing and
  carries its own tests.
- **Cost past free tier:** Ntropy free tier is 2,000 txns; a heavy user exceeds that.
  Usage-based pricing is fine for a single-owner MVP but should be watched.
